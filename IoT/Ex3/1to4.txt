IoT Exercise 3

1. Network configuration

The system runs through Docker Compose and consists of three cameras, two Fog nodes, a Cloud node and a Logger. Four networks were created: zone_a_net (1.1.2.0/24) connects Cameras 1 and 2 to Fog A, zone_b_net (1.1.3.0/24) connects Camera 3 to Fog B, backbone_net (1.1.1.0/24) connects the Fog nodes to the Cloud, and mgmt_net (1.1.4.0/24) is used for logging. Static IPs are assigned to the containers. The Fog nodes are limited to 0.5 CPU cores and 256 MB RAM to simulate resource-constrained devices.

A 200 ms network delay is configured between the Fog nodes and Cloud using tc netem to simulate WAN latency.

Implementation: docker-compose.yml

Testing: `docker compose up --build -d`, `docker compose ps`, `docker compose exec fog_a ping -c 10 cloud` and `docker stats`.

2. Image processing

2.1 Local processing

Images up to 300 KB are processed locally by the Fog node. This avoids sending small images to the Cloud unnecessarily.

Implementation: fog.py and fc_utils.py.

2.2 Distributed processing

For larger images, the Fog node processes part of the image and sends the remaining work to the Cloud. Once the Cloud returns its result, the Fog combines the processed parts.

Implementation: fog.py, cloud.py and fc_utils.py.

2.3 Adaptive processing

The amount of work performed locally depends on the Fog node's CPU utilisation. Images up to 300 KB are processed entirely locally. For larger images, the Fog processes 75% locally when CPU utilisation is below 5%, 50% below 10%, and 25% at or above 10%. The remaining work is sent to the Cloud. CPU utilisation is measured using psutil.

Implementation: fog.py.

2.4 Image verification and storage

After processing, the Fog verifies the resulting image using SHA-256 hashes of the decoded pixel data. This checks that the image has not been modified during processing. After successful verification, the image is sent to the Cloud and stored under a directory corresponding to the camera's IP address.

Implementation: fc_utils.py, fog.py and cloud.py.

Testing: Send images of different sizes through the cameras and check the Fog and Cloud logs. Check stored images with `docker compose exec cloud ls -R /cloud/images`.

3. Logging and monitoring

3.1 Logging

The Fog and Cloud nodes generate JSON logs containing information such as the service, timestamp, client IP, request, request size, processing time and response status.

Implementation: fog.py, cloud.py and fc_utils.py.

3.2 Centralised logging

A separate Logger container receives logs from the Fog and Cloud nodes through the management network. The records are appended to `/logs/system.jsonl`. A persistent volume ensures that logs remain available after the Logger container restarts.

Implementation: log.py, fc_utils.py and docker-compose.yml.

3.3 Alerting

An alert is generated whenever a Fog node reports a failed image verification (`verified: false`). The Logger writes a separate alert entry to the central log file. To test this, the Cloud was temporarily modified to change one pixel in its second processing response. This causes the Fog node's hash verification to fail while keeping the image valid.

Implementation: log.py, fog.py and temporarily cloud.py.

Testing: `docker compose exec logger cat /logs/system.jsonl`. The log should contain the verification failure and a separate alert entry with `type` set to `alert`.

4. Security

4.1 TLS and mTLS

A private CA was created to sign certificates for the Fog and Cloud nodes. Camera-to-Fog communication uses TLS, allowing the cameras to verify the Fog server's certificate. Fog-to-Cloud communication uses mTLS. Both sides present certificates signed by the CA, and the Cloud requires a valid client certificate before accepting connections.

Implementation: certs/, camera.py, fog.py, cloud.py and docker-compose.yml.

Testing: Send requests through the cameras and verify that communication succeeds. Connections to the Cloud without a trusted client certificate should be rejected.

4.2 API token authentication

Each camera has a unique API token stored in the .env file. Docker Compose passes the corresponding tokens to the camera and Fog containers. The camera includes its token in the Authorization header as a Bearer token. The Fog checks the token against the expected value for that camera and rejects invalid tokens with HTTP 401.

Implementation: .env, .gitignore, docker-compose.yml, camera.py and fog.py.

Testing: Send a request with a valid token and verify that it is accepted. Change the token to an invalid value and verify that the Fog rejects the request with HTTP 401.
